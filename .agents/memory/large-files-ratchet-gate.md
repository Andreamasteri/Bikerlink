# 800-line ratchet gate

## ⛔ BLOCCO TOTALE — nessun split senza approvazione utente

**Regola assoluta e non negoziabile:** nessun agente può splittare un file per nessuna ragione senza approvazione esplicita dell'utente. Quando il gate fallisce, l'agente si ferma, segnala all'utente, e attende il via libera — non procede autonomamente.

**Why:** l'utente ha stabilito questa regola perché split autonomi introducono rischio senza consenso informato, possono catturare stato incompleto, e bypassano la governance del progetto. Il gate che fallisce è il segnale di chiedere, non di agire.

**How to apply:** se `check-large-files-ratchet.ts` (o post-merge, pre-commit, o file-conflict-guard) fallisce segnalando un file nuovo oltre 800 righe — STOP. Non splittare. Non creare file `-extra`. Non usare marker ALLOW. Segnala all'utente il nome del file, il conteggio righe, e attendi istruzioni esplicite.

---

## Valori numerici correnti

`scripts/check-large-files-ratchet.ts` (+ `scripts/lib/large-files-core.ts`) enforces a per-file
TS/TSX line limit. It runs inside `scripts/post-merge.sh` after every task merge.

**Gate threshold: 800 righe** — blocca qualsiasi file nuovo che superi 800 senza marker.
**Split target: ≤600 righe** — quando un file sfora 800 e va splittato (solo dopo approvazione utente), i file risultanti (sorgente + destinazione) devono stare entrambi sotto 600, non 800. Così c'è ~200 righe di margine prima che il gate scatti di nuovo.

**Line counting:** `content.split("\n").length` — this is `wc -l` + 1 for files that end in a
trailing newline. The `.large-files-baseline` numbers were generated by the same counter, so compare
against split-length, NOT `wc -l`. To drop a LEGACY file "under baseline N", its split-length must be
`<= N` (the gate fails only on `lines > baseline`).

---

## Rule classes

- NEW file > 800 and not in baseline → blocked. **NON splittare autonomamente — chiedere approvazione utente prima.** Oppure get a user-authorized marker.
  When splitting (after approval), ensure all resulting files are ≤600 lines.
- LEGACY file (in `.large-files-baseline`) → blocked only if it GROWS above its stored count.
- LOCKED marker file → drift > +5 over declared limit blocked; raising the declared limit is blocked.
- `--update-baseline` is HUMAN-ONLY (needs `BIKERLINK_HUMAN_BASELINE_UPDATE=1`). Agents must not use it.

**Why this matters:** the gate runs post-merge on `main`. If a merged task lands an offending file,
the post-merge script exits 1 and **every following merge keeps failing on the same files** until they
are fixed directly on main — the failure is sticky and not specific to the new task. Resolve by
splitting/trimming the offending files on main (a pure mechanical extraction verified by typecheck is
enough), not by touching the failing task.

**How to apply:** when a post-merge failure cites the "Ratchet 800 righe" gate, read the named files,
split new oversized components into sibling files (move their styles too), keep each result ≤600 lines.
Re-run `npx tsx scripts/check-large-files-ratchet.ts` and both typechecks before finishing.

**i18n files (`lib/i18n/en.ts`, `lib/i18n/it.ts`) recur here:** every feature that adds translation
keys grows them past baseline, and the keys CANNOT be deleted (merged features use them). Non-destructive
fix: pack several flat dotted keys onto a single physical line (`"a": "x", "b": "y", ...`) in the same
logical group — line count drops while every key/value is preserved. Keep en/it symmetric. Full-project
`tsc --noEmit` often times out (>120s); since compaction changes no keys/values the typecheck state is
unchanged, so an `esbuild --bundle` syntax check on the two files is sufficient to confirm validity.

## Marker ALLOW: deve stare in PRIMA riga
`parseMarker` (in `scripts/lib/large-files-core.ts`) legge SOLO `line[0]` per riconoscere `LARGE-FILE-ALLOW:` (la seconda riga è guardata solo per il companion del marker LOCKED). Quindi il marker che esenta un file deve essere la **prima riga fisica** del file (dopo lo strip del prefisso commento). Altri commenti come `// @no-split` NON sono letti da nessuno script: sono puramente documentali e possono stare in qualunque posizione. Se un file grande (es. i `lib/i18n/<lang>.ts` fusi) ha l'ALLOW in seconda riga il gate fallisce comunque.
**Why:** durante il merge dei file i18n, mettere `// @no-split` in riga 1 e `// LARGE-FILE-ALLOW:` in riga 2 faceva fallire il ratchet pur avendo il marker; invertirle (ALLOW prima) risolve.

## Splittare gli script CLI sotto scripts/
`scripts/` è in IGNORE_DIRS del fixer fix-inline-default-memo-deps (non auto-scansiona sé stesso) ma NON in EXCLUDED_DIRS del ratchet → i nuovi file sotto scripts/ sono comunque soggetti al limite 800. Quando uno script CLI sfora, estrai la logica pura in moduli `scripts/lib/*` e tieni un main sottile come entrypoint.
**Why:** test/post-merge/check invocano lo script PER PATH; il path dell'entry NON deve cambiare durante lo split, altrimenti rompi gli invocatori.
