# spatial_ref_sys publish failure (PostGIS + Replit provisioning)

## Symptom
Publishing fails during the "Creating Autoscale service" / provision step with:
```
Failed to run database migration statement
ALTER TABLE "spatial_ref_sys" ADD PRIMARY KEY ("srid");
must be owner of table spatial_ref_sys
```
(PostgreSQL error 42501 — insufficient_privilege.)

## Root cause
- The DDL is generated by **Replit's own internal schema-migration step**, run on the **copy-dev→prod = OFF** path. It is NOT our `deploy-build.sh`, NOT `server/migrate.ts`, NOT our `drizzle.config.ts`.
- That internal migration **ignores our `drizzle.config.ts` filters** (`extensionsFilters: ["postgis"]`, `tablesFilter: ["!spatial_ref_sys"]`). Restoring/confirming those filters does NOT prevent the error — confirmed by live test.
- Our app's DB user is **not the owner** of the PostGIS system table `spatial_ref_sys`, so the `ALTER TABLE ... ADD PRIMARY KEY` fails. We cannot change ownership (no superuser). Owner differs dev vs prod (dev `postgres`, prod `cloud_admin`/Neon), which is why the diff thinks it must alter it.

## Build-log evidence (2026-05-31)
- copy **ON** + current deploy-build.sh (no `.cache/` removal) → **SUCCESS** (e.g. build 08aa14ff). Replit copies data, runs no schema diff → no spatial_ref_sys DDL.
- copy **ON** + old deploy-build.sh (had `rm -rf .cache/`) → FAIL (Permission denied on `.cache/`, a separate already-fixed bug).
- copy **OFF** → always FAIL on spatial_ref_sys, regardless of build script. Error surfaces in the Publish UI during promote; it does NOT appear in the downloadable build logs.

## Status / resolution
- **Cannot be fixed from our codebase.** Escalated to Replit support.
- **copy ON is not an acceptable workaround** once real prod users exist — it wipes the production DB by overwriting it with dev data. Safe only pre-launch.

**Why:** the failing DDL runs at Replit's platform level with our non-owner DB role; no app-side config has been found that suppresses it on the copy-OFF path.
**How to apply:** if this error reappears, do NOT re-investigate drizzle.config.ts filters or deploy-build.sh — both are already ruled out. Either wait for the Replit support fix, or (pre-launch only) publish with copy ON.

## Runtime PostGIS is safe — only migrations are the risk
The deploy failure is caused exclusively by **schema-diff/migration** DDL touching the PostGIS system table. **Calling PostGIS functions at runtime is fine** and does NOT trigger it. So when a task asks for PostGIS point-in-area matching, prefer runtime `ST_Contains(ST_MakeEnvelope(minLon,minLat,maxLon,maxLat,4326), ST_SetSRID(ST_MakePoint(lon,lat),4326))` built from values passed as query params (e.g. `unnest(...)::float8[] WITH ORDINALITY`) — no new table, no migration, no deploy risk. PostGIS itself is already enabled (migration 0041).
**Why:** satisfies a "use PostGIS" requirement without re-introducing the copy-OFF deploy failure.
