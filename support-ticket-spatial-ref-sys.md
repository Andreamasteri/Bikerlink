# Replit Support Request — Deploy permanently blocked by PostGIS `spatial_ref_sys` ownership mismatch after the automatic Neon → Helium database upgrade

## Subject (paste into the support form)

Deploy blocked: publish-time schema diff generates `ALTER TABLE spatial_ref_sys ADD PRIMARY KEY` and fails with `42501 must be owner of table spatial_ref_sys` — caused by the automatic dev DB Neon→Helium upgrade changing the table owner.

---

## TL;DR

After Replit automatically upgraded my **development** database from Neon to Helium, the owner of the PostGIS system table `spatial_ref_sys` changed in development (now `postgres`) while production still has it owned by `cloud_admin`. Replit's publish-time schema diff now detects this as drift and emits:

```
ALTER TABLE "spatial_ref_sys" ADD PRIMARY KEY ("srid")
```

which **always fails** in production because the application role is not the owner of that PostGIS system table:

```
ERROR: must be owner of table spatial_ref_sys (SQLSTATE 42501)
```

This blocks every deploy. **Nothing in my codebase issues this DDL** — it is generated by Replit's publish/deploy pipeline. I spent **over 24 hours** isolating this before concluding it is a platform-level issue tied to the database upgrade. I need help unblocking the deploy.

## The exact error

During publish/deploy the pipeline runs a schema diff between development and production and produces:

```sql
ALTER TABLE "spatial_ref_sys" ADD PRIMARY KEY ("srid");
```

Result:

```
ERROR: must be owner of table spatial_ref_sys
SQLSTATE: 42501 (insufficient_privilege)
```

`spatial_ref_sys` is a **PostGIS system table** (≈8,500 EPSG coordinate-system rows) created automatically by `CREATE EXTENSION postgis`. The application database role is intentionally not its owner, so any `ALTER` on it is rejected.

---

## Root cause (with evidence)

I queried both environments. The primary key **already exists in both** — the only meaningful difference is the **owner role**, which diverged because of the dev DB upgrade:

| | Development (Helium) | Production |
|---|---|---|
| Has primary key on `srid` | ✅ yes (`spatial_ref_sys_pkey`) | ✅ yes |
| Row count | 8,500 | 8,500 |
| **Table owner** | **`postgres`** | **`cloud_admin`** |

Query used (identical in both environments):

```sql
SELECT
  (SELECT count(*) FROM pg_constraint
     WHERE conrelid = 'spatial_ref_sys'::regclass AND contype = 'p') AS has_pk,
  (SELECT pg_get_userbyid(relowner) FROM pg_class
     WHERE relname = 'spatial_ref_sys') AS owner,
  (SELECT count(*) FROM spatial_ref_sys) AS rows;
```

### Why this happened

This maps directly onto your own documentation:
**https://docs.replit.com/references/data-and-storage/database-upgrade**

- The Neon → Helium upgrade is automatic, runs once per app, and **updates `DATABASE_URL`** to point at Helium.
- On **Neon**, the PostGIS system table was owned by `cloud_admin`.
- On **Helium** (the new dev DB), PostGIS was set up under the `postgres` role, so `spatial_ref_sys` is now owned by `postgres` in development.
- **Production was not part of the upgrade**, so it still has `spatial_ref_sys` owned by `cloud_admin`.

The result is a **dev/prod owner mismatch on a PostGIS system table**, which the publish-time schema diff interprets as drift and tries to "fix" with an `ALTER TABLE ... ADD PRIMARY KEY`, which can never succeed.

### Timeline that confirms it

- Publishes on **May 19, 20, 21, and 28** succeeded — at that time **both** dev and prod were on Neon, so `spatial_ref_sys` had the **same owner in both** and the diff produced nothing.
- After the dev DB was upgraded to Helium, publishes on **May 29** began failing on this exact statement.
- The failure is therefore **not correlated with any application code change** — it is correlated with the infrastructure upgrade.

### Additional anomaly worth flagging

Your upgrade documentation states that after a completed upgrade the `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD` variables are **removed** and the old Neon string is saved as `NEON_DATABASE_URL`. In my environment:

- `DATABASE_URL` **does** point to Helium, **but**
- `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` are **still present**, and
- `NEON_DATABASE_URL` is **not present** in Secrets.

This suggests the upgrade may have completed only partially, which may be related to the ownership inconsistency above.

### The platform contradicts itself here

Your own shared-database migration guide instructs data transfers to use:

```
pg_dump  ... --no-owner --no-privileges
pg_restore ... --no-owner --no-privileges
```

i.e. Replit deliberately **strips ownership and privileges** when moving data, precisely to avoid ownership conflicts. Yet the **publish-time schema diff does the opposite**: it emits an ownership-sensitive `ALTER` against a PostGIS system table that no application role owns. The diff should apply the same `--no-owner` philosophy and skip extension-owned system objects.
